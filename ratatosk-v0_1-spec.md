# Ratatosk v0.1 — спецификация

**Статус:** драфт для реализации. Заменяет линейку v1.x полностью.

**Принцип документа:** сюда попадает только то, что команда из 3–4 человек может реализовать и оттестировать за ~18 месяцев. Всё остальное — в раздел 15 «Вне области» с явной формулировкой, чего продукт **не** делает. Обещания в UI обязаны соответствовать разделу 14, а не намерениям.

---

## 1. Область v1

**Есть:**
- 1:1 текстовые сообщения
- Передача файлов
- Группы на sender keys, исключение участника — социальное (см. 11.4)
- Транспорты: LAN, Tor onion-to-onion, почта (chatmail) поверх Tor
- Платформы: Android и десктоп (Linux, Windows) — разрабатываются параллельно на общем ядре

- Десктоп в режиме компаньона к телефону (см. 13.4)

**Нет:** звонков, голосовых сообщений, независимых устройств с общей идентичностью, персон, iOS/macOS, TURN/STUN, любой собственной серверной инфраструктуры, I2P, Yggdrasil, DHT-поиска, файлового роя, PoW, криптографической эвикции из групп.

**Единственная внешняя инфраструктура** — публичные chatmail-серверы (стандартный SMTP/IMAP). Свои мы не пишем и не держим; пользователь может указать любой, включая собственный.

## 2. Модель угроз

### 2.1. От чего защищаемся

| Противник | Что не получает |
|---|---|
| Пассивный наблюдатель сети (провайдер, Wi-Fi) | Содержимое, адресат, факт использования Ratatosk (весь трафик — Tor) |
| Chatmail-сервер | Содержимое, IP-адреса сторон, реальные личности |
| Активный сетевой атакующий | Подмену и вставку сообщений, понижение версии протокола |
| Атакующий, получивший ключи сегодня | Содержимое прошлых сообщений (forward secrecy) |
| Атакующий с физическим доступом к выключенному устройству | Содержимое БД (при заданном PIN) |

### 2.2. От чего НЕ защищаемся — и это должно быть в UI

- **Chatmail-сервер видит псевдонимный социальный граф**: какие адреса кому пишут, когда и какого размера. Адреса случайны и не связаны с личностью, IP скрыт Tor'ом, но граф связей и тайминги — видны. Это цена асинхронной доставки без своей инфраструктуры.
- **Скомпрометированное устройство** — полный доступ ко всей переписке. Никакой защиты нет и быть не может.
- **Участник группы** может слить содержимое и состав. Исключение участника — социальное действие, а не криптографическое (см. 11.4).
- **Post-compromise security ограничен**: восстановление после компрометации происходит при следующем полном рукопожатии (см. 8.5), а не мгновенно.
- **Первое сообщение новому контакту** имеет более слабую forward secrecy — свойство паттерна Noise IK (см. 8.2).
- **Глобальный наблюдатель**, видящий вход и выход Tor, может коррелировать по таймингам. Против него не защищает никто.

## 3. Идентичность

Одна идентичность на установку. Мультиустройственность и персоны — вне v1.

**Ключевой материал** генерируется при первом запуске из 32 байт CSPRNG:

| Ключ | Тип | Назначение |
|---|---|---|
| `IK` | X25519 | статический ключ Noise, долговременная идентичность |
| `SK` | Ed25519 | подпись групповых блоков и профиля |
| `onion_key` | Ed25519 | ключ onion-сервиса (v3) |
| `db_key` | 32 байта | шифрование локальной БД |

`IK` и `SK` выводятся из общего seed: `seed → BLAKE3_derive_key("ratatosk v0 ik" / "ratatosk v0 sk")`. `onion_key` генерируется независимо (его формат задан спецификацией Tor).

**Отпечаток** для верификации людьми: `BLAKE3(IK ‖ SK)`, первые 32 байта, выводятся 6 группами по 4 символа из алфавита base32 без похожих знаков.

**Резервная копия.** Seed отображается как 24 слова BIP39. Она восстанавливает **идентичность, но не историю** — переписка и список контактов остаются на устройстве. Так и написать в UI: «эта фраза вернёт вам ваш адрес, но не ваши сообщения».

**Ротация ключей — вне v1.** Компрометация идентичности = создание новой и переустановление контактов вручную. Механизм отзыва — фаза 2.

## 4. Адресация и обмен контактами

### 4.1. Контакт-карточка

```cbor
ContactCard = {
  1: bytes,     ; IK, 32
  2: bytes,     ; SK, 32
  3: tstr,      ; onion-адрес, "xxxxx.onion"
  4: tstr,      ; chatmail-адрес, "a7f3k9@nine.example"
  5: tstr,      ; отображаемое имя (не доверенное)
  6: uint,      ; версия карточки
}
```

Кодируется в URI `ratatosk:v0:<base32(deterministic CBOR)>` и отображается QR-кодом. Размер — около 200 байт, в QR помещается свободно.

### 4.2. Способы обмена

1. **QR-код при личной встрече** — основной. Отпечаток проверять не нужно: канал доверенный по построению.
2. **Ссылка через другой канал** — с обязательным экраном «сверьте отпечаток по голосовой связи» и явной пометкой контакта как непроверенного, пока сверка не подтверждена.

### 4.3. Обновление карточки

Смена chatmail-адреса или onion-адреса рассылается существующим контактам как подписанное `SK` сообщение `CardUpdate` с монотонной `версией`. Получатель принимает только строго большую версию. Ключи `IK`/`SK` в `CardUpdate` меняться не могут — это уже другая идентичность.

## 5. Транспорты

### 5.1. LAN

- Обнаружение: mDNS, сервис `_ratatosk._tcp`, в TXT-записи — ротируемый маяк:
  `beacon = nonce(8) ‖ BLAKE3_derive_key("ratatosk v0 beacon", IK ‖ floor(unix/900) ‖ nonce)[0..8]`
- Контакт пересчитывает значение для каждого известного `IK` и слотов `−1, 0, +1`. Посторонний видит шум, меняющийся каждые 15 минут. Статичный идентификатор в эфир не транслируется никогда.
- Соединение: TCP, поверх — тот же Noise-канал, что и везде.
- **По умолчанию LAN выключен.** Он раскрывает факт использования Ratatosk в локальной сети; включается сознательно, с объяснением в UI.

### 5.2. Tor onion

Каждое устройство поднимает onion-сервис v3 через встроенный arti (версия 2.x, где поддержка скрытых сервисов стабильна). Это одновременно решает:
- NAT-traversal — у onion-адреса нет NAT, hole punching не нужен, STUN/TURN не нужны;
- стабильную адресацию при смене сети — адрес не зависит от IP;
- сокрытие IP обеих сторон.

Цена: 300–800 мс односторонней задержки, единицы секунд на установление, десятки мегабайт памяти на Tor-клиент.

### 5.3. Chatmail поверх Tor

Почта используется как **тупая труба для наших же запечатанных кадров**. OpenPGP, Autocrypt и любые почтовые схемы шифрования не применяются — криптостек в системе один.

- Отправка: SMTP через SOCKS-прокси arti.
- Приём: IMAP IDLE через тот же прокси.
- Тело письма: `Content-Type: application/octet-stream`, base64, один или несколько кадров.
- Заголовки: `Subject` — фиксированная строка `Ratatosk`; `From`/`To` — chatmail-адреса; всё остальное минимизируется. Никакой информации в заголовки не выносится.
- Аккаунт создаётся автоматически при первом запуске на выбранном chatmail-сервере (эти серверы допускают регистрацию без персональных данных). Адрес — случайные 6–8 символов.

**Ограничение размера.** Кадр в почте округляется до класса из 5.5. Письмо не должно превышать 20 МБ; файлы больше 20 МБ передаются только прямым каналом (см. 10.3).

### 5.4. Выбор транспорта

Не гонка. Строгая последовательность с таймаутами:

1. Если контакт виден в LAN и LAN включён → LAN.
2. Иначе попытка соединения с onion-адресом, таймаут 45 с.
3. Если не удалось → отправка почтой.

Одновременная отправка одним и тем же сообщением по нескольким транспортам запрещена. Дублирование на приёме допускается и разрешается дедупликацией (9.2) — например, если сообщение ушло почтой, а потом контакт появился онлайн.

**Единственное исключение:** LAN и Tor не смешиваются в одной сессии никогда. Сессия, начатая в LAN, при потере связи не продолжается через onion — устанавливается новая. Иначе локальный наблюдатель связывает LAN-присутствие с onion-активностью.

### 5.5. Классы размера кадра

| Класс | Размер | Применение |
|---|---|---|
| S | 4 КиБ | текст, служебные сообщения, квитанции |
| M | 64 КиБ | превью, мелкие файлы, групповые блоки |
| L | 1 МиБ | чанки файлов |

Каждый кадр дополняется до размера своего класса. Паддинг находится **внутри** AEAD (см. 7.2), поэтому аутентифицирован и не может служить скрытым каналом.

Три класса вместо одного — сознательный компромисс: одиночный фиксированный размер удобнее для анализа устойчивости, но 4 КиБ на квитанцию о прочтении при почтовом транспорте неприемлемы по трафику и батарее.

## 6. Сериализация

**Детерминированный CBOR** (RFC 8949 §4.2) для всего: ключи по возрастанию, минимальная длина, никаких неопределённых длин. Реализация — `ciborium`.

Причина отказа от protobuf: мы считаем хэши и подписи от структур, а protobuf не нормирует байтовое представление (порядок полей, минимальность варинтов, порядок map). Два честных клиента получили бы разные хэши одной структуры.

**Правило:** подпись и хэш вычисляются **над принятыми байтами**, а не над результатом повторной сериализации. Неизвестные ключи сохраняются как непрозрачный остаток и не переупорядочиваются.

Каждая структура несёт `protocol_version: uint` первым ключом. Клиент отвергает старшие мажорные версии с понятным сообщением.

## 7. Кадр

### 7.1. Структура

```
frame = header ‖ ciphertext ‖ tag
header = version(1) ‖ type(1) ‖ session_id(8) ‖ counter(8) ‖ nonce(24)
```

- `type`: `0x01` handshake, `0x02` данные
- `session_id`: 8 байт, из хэша транскрипта Noise (см. 8.3) — 64 бита делают коллизии практически невозможными, в отличие от 32
- `counter`: номер сообщения в отправляющей цепочке, монотонный, не сбрасывается
- Общий размер = размер класса

### 7.2. Шифрование

```
plaintext  = payload ‖ 0x80 ‖ 0x00 * k
ciphertext ‖ tag = XChaCha20-Poly1305(key, nonce, aad = header, plaintext)
```

**AAD равен всему заголовку.** Это обязательно: без этого `counter` не аутентифицирован, и подделанный заголовок заставляет получателя выводить тысячи ключей до провала проверки.

### 7.3. Приём

1. Проверка размера (совпадает с одним из классов) и `version`/`type`.
2. Поиск сессии по `session_id`.
3. Вывод ключа **ровно для позиции `counter`**, проверка тега. Только после успеха достраиваются и кэшируются пропущенные ключи. Это ограничивает стоимость мусорного кадра одной операцией независимо от заявленного счётчика.
4. Не нашли сессию / не прошёл тег → отбросить, инкрементировать счётчик аномалий по источнику.

Trial decryption по всем контактам не выполняется — для handshake есть отдельный путь (8.3).

## 8. Криптография

### 8.1. Примитивы

| Назначение | Алгоритм | Крейт |
|---|---|---|
| Обмен ключами | X25519 | `x25519-dalek` |
| Подпись | Ed25519 | `ed25519-dalek` |
| AEAD | XChaCha20-Poly1305 | `chacha20poly1305` |
| Хэш, KDF | BLAKE3 (`derive_key`) | `blake3` |
| KDF из PIN | Argon2id | `argon2` |
| Затирание | — | `zeroize` |

Собственных реализаций примитивов нет. Собственный код — только их комбинирование, в одном модуле, покрытом тест-векторами.

### 8.2. Рукопожатие: Noise IK

Паттерн `Noise_IK_25519_ChaChaPoly_BLAKE2s` (реализация — `snow`; BLAKE2s взят как штатный для Noise, BLAKE3 используется вне Noise).

`IK` — «инициатор знает статический ключ получателя». У нас он всегда известен: он в контакт-карточке. Отсюда следуют три вещи, важные для реализуемости:

- **Пул одноразовых предключей не нужен.** Вся механика X3DH с prekey-бандлами, их пополнением, исчерпанием и гонками исчезает целиком.
- **Транскрипт входит в вывод ключей по построению Noise.** Понижение версии и подмена идентичности невозможны без дополнительных мер — это свойство конструкции, а не наша защита, которую можно забыть.
- **Первое сообщение асинхронно.** Инициатор шлёт `-> e, es, s, ss` и полезную нагрузку одним сообщением, получатель может быть офлайн.

**Честное ограничение.** В `IK` полезная нагрузка первого сообщения защищена только статическим ключом получателя: компрометация `IK` получателя в будущем раскрывает записанное первое сообщение. Последующие сообщения этим не затронуты. Клиент не отправляет в первом сообщении ничего, кроме приветствия и своей карточки; содержательная переписка начинается после ответа.

### 8.3. Установление сессии

```
транскрипт h — как определено Noise
session_id = BLAKE3_derive_key("ratatosk v0 sid", h)[0..8]
root_key   = BLAKE3_derive_key("ratatosk v0 root", h ‖ noise_output)
ck_send / ck_recv = BLAKE3_derive_key("ratatosk v0 chain-a" / "chain-b", root_key)
```
Инициатор берёт `chain-a` как отправляющую, получатель — наоборот.

Handshake-кадр адресуется получателю по `session_id`, вычислить который заранее нельзя. Поэтому handshake-кадры имеют `session_id = 0` и обрабатываются отдельной веткой: получатель пробует расшифровать своим статическим ключом (одна операция — в `IK` получатель не перебирает контакты). Это устраняет всю проблему rate-limited trial decryption, ради которой в старой спецификации существовал PoW.

**Anti-replay handshake:** получатель хранит `BLAKE3(e ‖ ciphertext)` обработанных рукопожатий, TTL 30 суток, ёмкость 100 000, вытеснение LRU. Повтор отбрасывается.

### 8.4. Ретчет

Симметричный, без DH-шага:

```
message_key_n = BLAKE3_derive_key("ratatosk v0 msg", ck_n)
ck_{n+1}      = BLAKE3_derive_key("ratatosk v0 chain", ck_n)
```
Ключ сообщения стирается сразу после использования — это даёт forward secrecy.

**Пропущенные ключи.** Почтовый транспорт доставляет с перестановками и задержками. Кэш пропущенных ключей: до 2000 на сессию, до 200 000 на устройство, TTL 30 суток, вытеснение — самые старые.

### 8.5. Post-compromise security

Полноценный Double Ratchet с DH-шагом в v1 **не реализуется** — он плохо сочетается с почтовым транспортом (шаг требует ответа противоположной стороны, а задержка может быть сутки) и заметно усложняет код.

Вместо него: **полное повторное рукопожатие** при выполнении любого условия — прошло 7 суток, отправлено 1000 сообщений, обе стороны одновременно доступны прямым каналом. После него старые ключи бесполезны.

Это означает: восстановление после компрометации занимает до 7 суток, а не одно сообщение. Свойство должно быть указано в разделе 14 и не должно рекламироваться иначе.

### 8.6. Локальное хранилище

`db_key` шифруется `Argon2id(PIN)`; результат хранится в Android Keystore / OS-хранилище десктопа. Без PIN приложение не открывает БД. PIN опционален, но при отказе UI показывает, что содержимое доступно любому, кто получил устройство.

## 9. Сообщения

### 9.1. Конверт

```cbor
Envelope = {
  1: uint,        ; protocol_version
  2: bytes,       ; msg_id, 16 байт, случайные
  3: {            ; hlc — гибридные логические часы
       1: uint,   ;   wall_ms
       2: uint,   ;   logical
     },
  4: uint,        ; тип полезной нагрузки
  5: any,         ; полезная нагрузка
  6: ? bytes,     ; group_id
  7: ? [bytes],   ; causal_refs — msg_id непосредственных предшественников
  8: ? {1: bytes, 2: uint, 3: uint},  ; фрагмент: uid, index, total
}
```

`hlc` — источник порядка. Системное время не является источником порядка никогда: клиент отбрасывает `wall_ms`, опережающий локальное более чем на 5 минут, и упорядочивает по `hlc → causal_refs → msg_id`.

### 9.2. Дедупликация

По `msg_id`, окно 30 суток. Одно сообщение может законно прийти дважды разными транспортами — это нормальный режим, а не ошибка.

### 9.3. Фрагментация

Полезная нагрузка, не помещающаяся в класс кадра, режется на фрагменты. Ограничения: до 4096 фрагментов на сообщение, TTL незавершённой сборки — 30 суток (почта), 10 минут (прямой канал), суммарно не более 64 МиБ буферов, при переполнении вытесняются самые старые.

### 9.4. Квитанции

Доставка и прочтение — **только прямым каналом**. По почте квитанции не отправляются: каждая была бы отдельным письмом, что удваивает трафик, расход батареи и объём метаданных у сервера. В UI при почтовой доставке показывается «отправлено», без «доставлено»/«прочитано».

## 10. Файлы

### 10.1. Общая схема

Файл шифруется случайным `file_key` (32 байта), передаваемым в сообщении. Чанки нумеруются, `chunk_id = BLAKE3_derive_key("ratatosk v0 file", file_key ‖ index)`. Хэш для проверки целостности считается от шифротекста.

Content-addressing по хэшу открытого содержимого не применяется: он позволил бы проверять наличие у вас конкретного известного файла.

### 10.2. Прямой канал

Потоковая передача чанками по 1 МиБ (класс L), с возобновлением по индексу чанка. Параллелизма и роя нет — один отправитель, один получатель.

### 10.3. Почта

Файлы до 20 МБ — вложением в одном письме (или серией фрагментов). Больше 20 МБ — только прямым каналом; UI сообщает: «файл будет отправлен, когда получатель появится в сети».

Превью изображений — до 32 КиБ, класс M, идут вместе с сообщением всегда.

## 11. Группы

### 11.1. Модель

Sender keys. У каждого участника — своя отправляющая цепочка на группу, распространяемая всем остальным по 1:1-сессиям. Ratchet Tree, MLS и криптографическая эвикция **вне v1** (обоснование — в разделе 15).

```
sender_key_i^{n+1} = BLAKE3_derive_key("ratatosk v0 sender-chain", sender_key_i^n)
message_key        = BLAKE3_derive_key("ratatosk v0 sender-msg", sender_key_i^n)
```

Групповое сообщение **подписывается** `SK` отправителя. Без подписи любой участник мог бы подделать сообщение от имени любого другого — sender key одинаков у всех получателей. Следствие: отрицаемости внутри группы нет, и это надо сказать прямо.

### 11.2. Состав

OR-Set с метками HLC. Добавление и удаление — подписанные блоки, распространяемые по 1:1-сессиям каждому участнику. Порядок разрешается семантикой OR-Set: удаление действует на те добавления, которые удаляющий видел. Это корректно обрабатывает случай «исключили, пока он в другом сегменте сети заново вступал».

**Права:** в v1 любой участник может пригласить, только создатель — исключить. Ролевая модель — фаза 2.

### 11.3. Рассылка

Групповое сообщение отправляется **отдельной копией каждому участнику** по его 1:1-каналу. Отправка через `To:` со списком раскрыла бы состав группы chatmail-серверу.

Отсюда жёсткое ограничение: **максимум 32 участника в v1.** Сообщение в группе на 32 человека — это до 32 писем. Больше не потянет ни батарея, ни лимиты серверов.

### 11.4. Исключение — социальное, не криптографическое

Исключённый участник:
- не получает новых сообщений от честных клиентов;
- **сохраняет доступ ко всей прошлой переписке**;
- при модифицированном клиенте может продолжать читать, если хотя бы один участник ему пересылает.

Формулировка в UI: «Участник удалён. Он больше не получит новых сообщений, но сохранит доступ к прошлым. Для полной изоляции создайте новую группу».

### 11.5. Вступление

Новый участник получает от пригласившего: состав группы, контакт-карточки всех участников, текущие sender keys всех участников. Он **не может** расшифровать сообщения, отправленные до вступления, если только не сохранил их шифротексты заранее (в v1 это не считается угрозой — до вступления он их не получал).

При вступлении каждый участник обязан начать новую sender-цепочку. Это не даёт полноценной backward secrecy, но ограничивает окно.

Присоединение раскрывает всем участникам onion- и chatmail-адреса друг друга. Так и сказать при создании группы.

## 12. Хранилище

**SQLite** (`rusqlite`) + FTS5 для поиска. Чувствительные поля шифруются на уровне приложения ключом `db_key`; метаданные схемы остаются открытыми.

**Compaction — обязателен с первого дня.** Иначе клиент перестанет открываться на третий год.

- Причинный лог сообщений хранит `causal_refs` только для окна в 1000 последних сообщений; дальше — линейный порядок по HLC, ссылки отбрасываются.
- Tombstones удалённых сообщений живут 90 суток, затем схлопываются.
- Раз в 5000 сообщений группа фиксирует снапшот состава; всё предшествующее в OR-Set сворачивается в baseline.
- Кэш пропущенных ключей и окно дедупликации чистятся по TTL из 8.4 и 9.2.

**Экспорт:** переписка выгружается в зашифрованный архив (тот же `db_key`, ключ показывается пользователю). Это единственный путь переноса истории на другое устройство в v1.

## 13. Платформы

### 13.1. Android

- Foreground service с постоянным уведомлением — обязателен: без него систему поддерживать onion-сервис и IMAP IDLE нельзя.
- Запрос на исключение из оптимизации батареи при первом запуске, с объяснением. Без него доставка будет прерывистой.
- arti встроен в процесс; Tor bootstrap — при старте сервиса.
- IMAP IDLE поверх SOCKS arti; при разрыве — переподключение с экспоненциальным backoff.
- Минимальная версия: Android 9. `minSdk` ниже не окупается.
- Ожидаемый расход батареи следует измерить и указать в описании приложения честно.

### 13.2. Десктоп

- Tauri поверх того же ядра, autostart в трее.
- Linux и Windows в v1; macOS вне области.
- Десктоп работает **в режиме компаньона** (см. 13.4), а не как самостоятельная идентичность.

### 13.4. Режим компаньона

Телефон — единственный носитель идентичности и единственное хранилище истории. Десктоп является терминалом к нему. Собственных `IK`/`SK`, собственного onion-адреса и собственного chatmail-аккаунта у десктопа нет; для всех контактов существует **один** пользователь.

Это не функция протокола, а локальный RPC поверх уже построенных механизмов — новых криптографических конструкций не вводится.

**Сопряжение.** Телефон показывает QR с `pairing_key` (X25519, генерируется на сопряжение) и способом подключения. Десктоп устанавливает Noise IK-сессию к телефону — тот же паттерн, тот же кадровый формат, что и для контактов. Сопряжённые устройства перечислены на телефоне, отзыв — удаление записи и немедленный разрыв сессии.

**Канал.**
1. Если оба в одной сети — TCP по LAN, обнаружение по mDNS с маяком из 5.1.
2. Иначе — подключение к onion-сервису телефона.

Правило из 5.4 действует и здесь: сессия, начатая по LAN, при потере связи не продолжается через onion, а устанавливается заново.

**Что передаётся по каналу.** Только уже расшифрованные прикладные события: список чатов, сообщения, статусы, команды на отправку. Ключевой материал контактов, `IK`, `SK` и `db_key` границу устройства не пересекают никогда.

**Кэш на десктопе.** До 1000 последних сообщений на чат, зашифрованы ключом, производным от `pairing_key`, и удаляются при отзыве сопряжения или по таймауту в 30 суток без подключения. Без кэша пролистывание истории превращалось бы в поток запросов через Tor.

**Файлы.** Проходят через телефон. Передача файлов больше 20 МБ с десктопа разрешена **только когда оба устройства в одной сети** — иначе выгрузка идёт через мобильный канал телефона. UI сообщает об этом явно.

**Следствия, которые нужно принять:**
- Телефон офлайн или разряжен — десктоп не работает. Это главная причина, по которой такую модель со временем перерастают; для v1 она приемлема.
- Пока десктоп подключён, расход батареи телефона выше.
- Компрометация десктопа даёт доступ к кэшу и возможность отправлять сообщения от имени пользователя до отзыва сопряжения. Ключи при этом не утекают.

**Выигрыш** — отсутствие синхронизации ключей и истории между устройствами, то есть самой дорогой части настоящей мультиустройственности. Полноценный вариант (независимые идентичности устройств) остаётся в фазе 2.

### 13.3. Общее ядро

Rust, биндинги через UniFFI для Android, прямые вызовы на десктопе. В ядре: крипта, протокол, транспорты, хранилище, синхронизация. В клиентах — только UI и системная интеграция. Правило без исключений: никакой протокольной логики выше UniFFI-границы.

## 14. Что сказать пользователю прямо

Раздел существует, чтобы обещания продукта не разошлись со свойствами протокола. Формулировки идут в онбординг и в описание в сторе.

1. Сообщения доставляются мгновенно, только когда собеседник в сети. Иначе — через почтовый сервер, с задержкой до нескольких минут.
2. Почтовый сервер не видит содержимого и IP-адресов, но видит, какие адреса переписываются между собой и когда.
3. Удаление участника из группы не лишает его прошлых сообщений.
4. Резервная фраза возвращает адрес, но не переписку.
5. Программа на компьютере работает только тогда, когда телефон включён и в сети — она показывает то, что происходит на телефоне. Разрядился телефон — компьютер ничего не покажет.
6. Приложение постоянно висит в уведомлениях и расходует батарею. Иначе сообщения не приходят.
7. Звонков нет.

## 15. Вне области v1 — с обоснованием

| Что | Почему не сейчас |
|---|---|
| Криптографическая эвикция (MLS/TreeKEM) | Требует общего порядка коммитов, которого в модели без сервера нет. Совмещение с CRDT — открытая исследовательская задача, а не инженерная |
| Мультиустройственность с независимыми устройствами | Требует синхронизации ключей и истории — по сложности сравнимо с остальной v1. В v1 закрыто режимом компаньона (13.4), где телефон остаётся единственным носителем идентичности |
| Звонки | Собственный медиатранспорт + задержки Tor 300–800 мс. Отдельная фаза, и начинать надо с UDP-транспортов |
| iOS | Нет фоновых сокетов, лимиты NSE (~24 МБ, секунды CPU) не вмещают Tor-стек. Паритета с Android не будет |
| STUN/TURN | Не нужны: onion-адрес не имеет NAT |
| PoW против спама | Не нужен: в Noise IK получатель не перебирает контакты, дорогого trial decryption нет |
| Персоны | Требуют отдельного onion-сервиса и изоляции хранилища на персону |
| Файловый рой | Один отправитель — один получатель покрывает сценарий мессенджера |
| Отзыв ключей | Требует проработки распространения отзыва в сети без общего порядка |

## 16. Тестирование

Ключевая позиция, а не приложение к спецификации.

- **Детерминированная симуляция** (`turmoil` или `madsim`): вся сеть в одном процессе с виртуальным временем и фиксированным сидом. Обязательные сценарии: разделение сети на неделю с последующим слиянием; перестановка сообщений почтовым транспортом; отправка обоими транспортами одновременно; одновременное исключение участника в двух сегментах; переполнение кэша пропущенных ключей. Найденное расхождение воспроизводится по номеру сида.
- **`cargo-fuzz`** на разбор кадра, CBOR-десериализацию и парсинг контакт-карточек — с первого дня, в CI.
- **`proptest`** на инварианты: слияние OR-Set коммутативно и идемпотентно; каноническая сериализация делает round-trip; `decrypt(encrypt(x)) == x` при любых перестановках; ключ сообщения не выдаётся дважды.
- **Тест-векторы** на всю деривацию ключей, зафиксированные в репозитории.
- **Формальная модель:** для Noise IK берётся готовая модель из Noise Explorer, прогоняется в ProVerif. Собственная верификация нужна только для групповой части — и до её прогона утверждения о доказанных свойствах групп не публикуются.
